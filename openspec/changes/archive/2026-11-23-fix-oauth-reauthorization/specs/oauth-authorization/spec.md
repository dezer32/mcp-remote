# Spec Delta

## ADDED Requirements

### Requirement: Токен, отвергнутый после refresh, ведёт к полной авторизации
Если remote ответил 401 на запрос с токеном, который прокси получил через `refresh_token` при обработке предыдущего 401 этого же запроса, прокси MUST NOT выполнять refresh повторно. Прокси MUST удалить сохранённые токены, запустить полный флоу авторизации в браузере и после его успеха повторить запрос с новым токеном.

#### Scenario: Протухший grant
- **WHEN** сервер авторизации выдаёт по сохранённому `refresh_token` новый токен, а remote отвечает на запрос с ним `401` с `error="invalid_token"`
- **THEN** прокси открывает браузер для авторизации, а после неё повторяет запрос, и клиент получает ответ remote вместо ошибки

#### Scenario: Refresh даёт рабочий токен
- **WHEN** remote ответил 401 на истёкший токен, а токен, полученный refresh-ем, remote принимает
- **THEN** браузер не открывается, и клиент получает ответ remote

### Requirement: Токен, отвергнутый после полной авторизации, завершает запрос
Если remote ответил 401 на запрос с токеном, полученным полным флоу авторизации при обработке этого же запроса, запрос MUST завершиться ошибкой. В рамках этого запроса прокси MUST NOT открывать браузер повторно. Ошибка MUST сообщать, что токен отвергнут сразу после авторизации.

#### Scenario: Ресурс отвергает любой токен
- **WHEN** remote отвечает 401 на любой токен, и сохранённых токенов нет
- **THEN** браузер открывается ровно один раз, а клиент получает JSON-RPC ошибку о том, что токен отвергнут после авторизации

### Requirement: Повторы запроса после 401 ограничены
Прокси MUST повторять один запрос к remote после ответов 401 не более трёх раз. После исчерпания лимита запрос MUST завершиться ошибкой, без новых refresh и без открытия браузера.

#### Scenario: Remote всегда отвечает 401
- **WHEN** remote отвечает 401 на каждую попытку запроса
- **THEN** remote получает этот запрос не более четырёх раз, после чего клиент получает JSON-RPC ошибку

### Requirement: 401 на уже заменённый токен не запускает авторизацию
Если 401 пришёл на токен, который к моменту обработки ответа уже заменён (refresh или авторизацию выполнил другой запрос), прокси MUST повторить запрос с текущим токеном. Из-за такого ответа прокси MUST NOT выполнять refresh и MUST NOT открывать браузер.

#### Scenario: Параллельные запросы с одним протухшим токеном
- **WHEN** два запроса ушли с одним и тем же токеном, оба получили 401, и обработка первого ответа уже получила новый токен
- **THEN** второй запрос повторяется с новым токеном, а refresh или авторизация выполняется один раз на оба запроса

### Requirement: Callback-сервер поднимается на зарегистрированном порту
Если порт callback не задан явно, а у известного клиента (сохранённого после динамической регистрации или заданного `--static-oauth-client-info`) в `redirect_uris` есть URL со схемой `http`, тем же хостом, что у callback-сервера, и путём `/callback`, прокси MUST сначала попытаться поднять callback-сервер на порту из этого URL. Явно заданный порт MUST иметь приоритет.

#### Scenario: Повторная авторизация с сохранённым клиентом
- **WHEN** сохранённый клиент зарегистрирован с `redirect_uris: ["http://127.0.0.1:62505/callback"]`, порт не задан, и порт 62505 свободен
- **THEN** callback-сервер слушает `127.0.0.1:62505`, в URL авторизации `redirect_uri` равен `http://127.0.0.1:62505/callback`, и новая регистрация клиента не выполняется

#### Scenario: Явный порт
- **WHEN** порт callback задан явно как 3334, а сохранённый клиент зарегистрирован с портом 62505
- **THEN** callback-сервер слушает порт 3334

### Requirement: Клиент из динамической регистрации регистрируется заново при несовпадении redirect_uri
Если клиент получен динамической регистрацией, а итоговый callback URL не входит в его `redirect_uris` (порт занят, порт задан явно, либо `redirect_uris` пуст), прокси MUST до открытия браузера зарегистрировать клиента заново с текущим callback URL и сохранить новую регистрацию вместо старой. Без `registration_endpoint` прокси MUST записать предупреждение и продолжить с прежним клиентом.

#### Scenario: Зарегистрированный порт занят
- **WHEN** сохранённый клиент зарегистрирован с портом 62505, порт не задан, и порт 62505 занят другим процессом
- **THEN** callback-сервер слушает свободный порт, клиент регистрируется заново с новым callback URL, и в URL авторизации используется новый `client_id`

#### Scenario: Сохранённый клиент без redirect_uris
- **WHEN** сохранённый клиент, полученный динамической регистрацией, не содержит `redirect_uris`
- **THEN** перед открытием браузера клиент регистрируется заново, и сохранённая регистрация содержит текущий callback URL

#### Scenario: Сервер не поддерживает регистрацию
- **WHEN** callback URL не входит в `redirect_uris` сохранённого клиента, а в метаданных сервера авторизации нет `registration_endpoint`
- **THEN** в лог пишется предупреждение, и флоу продолжается с прежним клиентом

### Requirement: Статический клиент не регистрируется заново
Для клиента, заданного `--static-oauth-client-info`, прокси MUST NOT выполнять регистрацию. Если его `redirect_uris` непуст и не содержит итоговый callback URL, прокси MUST записать предупреждение, где названы callback URL и способ задать порт явно, и продолжить флоу.

#### Scenario: Порт статического клиента занят
- **WHEN** статический клиент задан с `redirect_uris: ["http://127.0.0.1:8080/callback"]`, порт не задан, и порт 8080 занят
- **THEN** callback-сервер слушает свободный порт, регистрация не выполняется, и в лог пишется предупреждение с callback URL

### Requirement: Причина 401 видна в debug-логе
На каждый ответ 401 от remote прокси MUST записать в лог на уровне debug значения параметров `error` и `error_description` из `WWW-Authenticate` (если они есть) и признак того, был ли в запросе токен. Значения токенов MUST NOT попадать в лог.

#### Scenario: Отказ с invalid_token
- **WHEN** прокси запущен с `--debug`, и remote ответил `401` с `WWW-Authenticate: Bearer error="invalid_token"`
- **THEN** в stderr есть запись debug-уровня с `error=invalid_token` и признаком отправленного токена, а самого токена в записи нет

### Requirement: Итоговая ошибка 401 содержит код ошибки сервера
Если запрос завершился ошибкой из-за ответа 401, сообщение ошибки MUST содержать значение параметра `error` из `WWW-Authenticate` последнего ответа (если оно было) и `error_description`, усечённый до 200 символов (если он был).

#### Scenario: Ошибка после авторизации
- **WHEN** запрос завершился ошибкой, потому что remote ответил `401` с `error="invalid_token"` на токен, полученный авторизацией
- **THEN** JSON-RPC ошибка, которую получает клиент, содержит `invalid_token`

### Requirement: Шаги повторной авторизации видны в логе
Прокси MUST записывать в лог: успешный refresh токена (debug), переход к полному флоу авторизации из-за отвергнутого токена (info), повторную регистрацию клиента с её причиной (info). Значения токенов, `refresh_token`, `client_secret` и `code` MUST NOT попадать в лог.

#### Scenario: Протухший grant в логе
- **WHEN** прокси запущен с `--debug`, refresh прошёл, а новый токен отвергнут
- **THEN** в stderr последовательно есть запись об успешном refresh и запись о переходе к полной авторизации, и ни в одной из них нет значений токенов

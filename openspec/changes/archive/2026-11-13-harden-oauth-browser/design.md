# Design

## Context

Мотивация описана в proposal.md (раздел Why), требования в `specs/oauth-authorization/spec.md` и `specs/request-headers/spec.md`. Здесь только текущее устройство кода, которое определяет подход.

- `internal/oauth/browser.go`: `DefaultOpener.Open(ctx, url string)` выбирает команду через `runtime.GOOS` и запускает её через `exec.CommandContext`. На Windows это `cmd /c start "" <url>`. Go экранирует аргумент кавычками только если в нём есть пробел или кавычка, поэтому `&` в URL доходит до `cmd.exe` без экранирования.
- `internal/oauth/flow.go`: `Provider.authorizeLocked` выполняет discovery, затем DCR, затем `buildAuthorizeURL` и `opener.Open`. Если opener вернул ошибку, URL печатается в stderr для ручного открытия. Все POST-запросы (DCR, token exchange, refresh) идут через `p.httpClient`, то есть `&http.Client{Timeout: 30s}` без `CheckRedirect`: Go по умолчанию следует до 10 редиректов и на 307/308 повторяет тело.
- `internal/oauth/discovery.go`: идентификатор AS (`asBase`) берётся из `authorization_servers[0]` (с обрезанным `/`) либо из origin `ServerURL`. Метаданные запрашиваются по `asBase + "/.well-known/oauth-authorization-server"`, на 404 подставляются дефолтные пути. Ни один URL не проверяется ни по схеме, ни по `issuer`/`resource`.
- `internal/oauth/callback.go`: обработчик `/callback` принимает любой метод и на первый же запрос отдаёт результат в `send` (через `sync.Once`). Ветка `?error=` не смотрит на `state`.
- `Provider` уже держит `cfg *config.Config`, так что `cfg.AllowHTTP` и `cfg.Resource` доступны без изменения сигнатур.
- Unit-тесты `internal/oauth` поднимают `httptest.NewServer` (то есть `http://`) и создают `config.Config` без `AllowHTTP`.

## Goals / Non-Goals

**Goals:**
- Закрыть путь от данных удалённого сервера к запуску процесса на хосте при любом `authorization_endpoint`.
- Одна функция проверки URL OAuth-эндпоинтов, применяемая везде, где URL от сервера используется для запроса или открытия.
- Не менять публичные контракты (`Opener`, `httpmcp.TokenProvider`, `proxy.*`): assert-блок в `main.go` остаётся как есть.

**Non-Goals:**
- Лимиты на размер тел ответов, атомарность и межпроцессная блокировка хранилища токенов, дедупликация параллельных 401. Это change `fix-remote-transport`.
- Правильное размещение well-known для issuer с путём (RFC 8414 §3.1) и fallback на OIDC discovery. Это корректность discovery, а не безопасность; проверка `issuer` от этого не зависит.
- Заголовки безопасности на HTML-странице callback и поддержка синтаксиса `$BROWSER` со списком через `:` и `%s`.

## Decisions

### 1. Две линии проверки: политика в Provider, санитария в Opener

`Provider` проверяет URL по политике проекта (`https`, а `http` только с `--allow-http`). `DefaultOpener` независимо проверяет то, что безопасно для любого вызывающего: схема `http`/`https`, есть хост, нет userinfo, нет пробельных символов. В браузер уходит `u.String()`, а не сырая строка.

Почему две линии: opener — это опасный сток (sink). Проверка только при discovery оставит его открытым для будущих путей кода. Проверка только в opener не может применить `--allow-http` (opener не видит конфиг) и срабатывает поздно, уже после DCR.

Если opener отказал из-за небезопасного URL (внутренний sentinel `errUnsafeURL`), `authorizeLocked` завершается ошибкой и **не** печатает URL в stderr: печать небезопасного URL приглашала бы пользователя открыть его вручную. Прочие ошибки opener-а (нет браузера и т.п.) по-прежнему печатают URL.

Пробельные символы запрещаются явно. Тогда Go передаёт URL дочернему процессу без кавычек и без изменений на любой платформе. `buildAuthorizeURL` кодирует пробелы в параметрах через `url.Values.Encode`, так что легитимный URL их не содержит.

### 2. Windows: `rundll32.exe url.dll,FileProtocolHandler <url>` вместо `cmd /c start`

`rundll32` не является командным интерпретатором: `&`, `|`, `^`, `%` для него просто символы строки. Путь абсолютный: `%SystemRoot%\System32\rundll32.exe`, а если `SystemRoot` пуст, то `rundll32.exe`. Так нет зависимости от `PATH`.

Выбор команды выносится в чистую функцию `browserCommand(goos, url string) (name string, args []string)`. Её можно покрыть табличным тестом на любой ОС CI, включая ветку Windows на Linux-раннере.

Рассмотренные альтернативы:
- Экранировать `cmd /c start` через `^&`: правила экранирования `cmd.exe` хрупкие, история CVE-2025-6514 и BatBadBut показывает, что на этом легко ошибиться.
- `ShellExecuteW` через `syscall.NewLazyDLL("shell32.dll")`: без дочернего процесса вообще, но это windows-only код с `unsafe`, который нельзя протестировать вне Windows.
- `explorer.exe <url>`: всегда возвращает код 1, ошибки не отличить от успеха.
- PowerShell `Start-Process`: именно через подстановки PowerShell эксплуатировалась CVE-2025-6514.

### 3. Единая проверка URL эндпоинтов: `validateEndpointURL(raw, allowHTTP)`

Функция возвращает `*url.URL` или ошибку. Условия: URL абсолютный, схема `https` (или `http` при `allowHTTP`), непустой хост, нет userinfo. Применяется:
- в discovery к `resource_metadata`, `authorization_servers[0]`, а после получения metadata к `authorization_endpoint`, `token_endpoint` и непустому `registration_endpoint`. Дефолтные пути строятся от уже проверенного `asBase`;
- в стоках: в начале `postToken` (покрывает и обмен кода, и refresh) и `registerClient`. Так проверяются и метаданные, загруженные с диска старой версией: refresh падает, существующая логика очищает токены и запускает полный флоу с новым discovery.

Альтернатива «проверять только в discovery» не покрывает `metadata.json` из хранилища.

### 4. `issuer`: точное сравнение с точностью до завершающего `/`

Сравниваются `strings.TrimSuffix(issuer, "/")` и `strings.TrimSuffix(asIdentifier, "/")`. Здесь `asIdentifier` — исходное значение `authorization_servers[0]` или origin `ServerURL` во fallback-ветке. Остальное сравнивается побайтово, как требует RFC 8414 §3.3. Отсутствующий `issuer` даёт `Warn` и продолжение: существующий код намеренно терпит неполные метаданные («плохой сервер не должен ломать клиент»), а при подконтрольном атакующему документе `issuer` защиты всё равно не даёт. На 404 (дефолтные пути) проверять нечего.

Почему не строгое равенство без нормализации: расхождение в завершающем `/` между `authorization_servers` и `issuer` — частая ошибка конфигурации, которая не несёт риска.

### 5. `resource`: тот же origin и иерархия пути

Схема и хост сравниваются без учёта регистра, порт — с учётом порта по умолчанию для схемы (`:443` для https равен отсутствию порта). Пути сравниваются после обрезки завершающего `/`: путь `ServerURL` должен быть равен пути `resource` или начинаться с `resourcePath + "/"`. Это граница сегмента, поэтому `/mcp` не покрывает `/mcp-admin`. Query и fragment у `resource` игнорируются.

Почему не строгое равенство по RFC 9728: MCP-серверы часто публикуют `resource` как origin, тогда как эндпоинт находится на `/mcp`. Строгое равенство сломало бы их. Иерархическое совпадение сохраняет нужное свойство: токен выпускается для нашего сервера или для дерева путей, в котором он лежит.

При явном `--resource` проверка пропускается: пользователь сознательно задал значение. Пустой `resource` даёт `Warn` и прежнее поведение (параметр `resource` не отправляется). Проверка выполняется только когда PRM реально использовался (был `resource_metadata` в `WWW-Authenticate`).

### 6. Политика редиректов OAuth-клиента через `CheckRedirect`

`p.httpClient` получает `CheckRedirect` с замыканием над `cfg.AllowHTTP`:
- если исходный запрос (`via[0].Method`) — POST, вернуть ошибку `redirect not allowed for <endpoint kind>`. `CheckRedirect` вызывается до отправки следующего запроса, поэтому тело никуда не уходит;
- если `len(via) >= 5`, вернуть ошибку;
- если предыдущий URL `https`, а новый `http`, и нет `AllowHTTP`, вернуть ошибку.

Cross-origin для GET discovery разрешён: в этих запросах нет секретов, а привязку документа к AS обеспечивает проверка `issuer`.

Альтернатива `http.ErrUseLastResponse` для POST вернула бы 3xx как обычный ответ. Тогда ошибка звучала бы как «status 307» без объяснения причины. Явная ошибка понятнее в логах.

### 7. Callback: невалидный запрос не завершает ожидание

Порядок в обработчике:
1. Метод не GET: ответ 405 с `Allow: GET`.
2. `subtle.ConstantTimeCompare(state, expected) != 1`: ответ 400 и HTML «invalid or missing state», без `send`.
3. Дальше прежняя логика (`error` → ошибка AS, нет `code` → ошибка, иначе успех) с `send`.

Почему не завершать флоу на неверный `state`: callback слушает `127.0.0.1:<port>`, туда может постучаться любой локальный процесс или страница в браузере. Легитимный редирект от AS всегда несёт `state`. Постоянное время сравнения скорее гигиена: длина `state` публична, а утечку времени через loopback практически не измерить.

### 8. Предупреждение о не-loopback `--host`

`authorizeLocked` после `listenCallback` проверяет `cfg.Host`: `localhost` (без учёта регистра) или IP, для которого `netip.Addr.IsLoopback()`, считаются loopback. Иначе, включая `0.0.0.0`, `::` и имена хостов, пишется `Warn`. Логгер есть только у Provider, поэтому проверка там, а не в `config.Parse` или `listenCallback`.

### 9. `Upgrade` в `reservedHeaders`

Добавляется ключ `"upgrade"` в map в `internal/config/config.go`. README, `docs/README.ru.md` и CLAUDE.md уже перечисляют его как зарезервированный, так что код догоняет документацию.

## Risks / Trade-offs

- [Строгие `issuer`/`resource` ломают криво настроенные серверы, которые работают сейчас] → ошибка называет оба значения. Для `resource` есть обход через `--resource`; для `issuer` обхода нет (решение пользователя: строго, с нормализацией). README получит пункт в troubleshooting.
- [AS, который не возвращает `state` в error-редиректе (нарушение RFC 6749 §4.1.2.1)] → пользователь увидит страницу 400, а флоу дождётся `--auth-timeout` вместо быстрой ошибки. Приемлемо: это сбой сервера, и страница объясняет причину.
- [Ветку Windows end-to-end в CI не проверить: браузер на раннере не открыть] → чистая `browserCommand` покрыта табличным тестом на всех ОС; перед релизом нужна ручная проверка OAuth на Windows (отдельная задача).
- [Метаданные, сохранённые старой версией с `http`-эндпоинтами] → одна полная переавторизация после обновления, без ручных действий.
- [`rundll32` и очень длинные URL] → URL авторизации обычно короче 1 КБ; вероятность нулевая, отдельных мер нет.

## Migration Plan

Миграции данных нет: формат `tokens.json`, `client.json` и `metadata.json` не меняется. В release notes перечислить пункты **BREAKING** из proposal. Откат — revert коммита: старая версия читает те же файлы.
